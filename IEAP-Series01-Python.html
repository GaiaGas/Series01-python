4. Start coding your ECG data processing pipeline using Git branches¶

Maybe you have some ideas for the decomposition in steps for your analysis... It is time to implement them!

The workflow is as follows:

  1. Create a new branch for the next step of your analysis.
  2. Implement the next step of your analysis in this new branch. Commit as often as needed and at least once per significant working change.
  3. Merge the branch into the main branch when you are happy with your changes.
  4. Repeat steps 1 to 3 for the next step(s) of your analysis.

4.1. Make clear what are the steps of your analysis¶

Before you start coding, it is important to make clear what are the steps of your analysis. You can do this by drafting the necessary steps in a markdown cell in your Jupyter notebook.

Method: to draft the necessary steps:

  • Start by the arrival point: what do you want to get at the end of your analysis?
  • Define the starting point: what do you have at the beginning of your analysis?
  • Think about the steps that are necessary to go from the starting point to the arrival point: how many steps? What is the order of these steps?

4.2. Create a new branch¶

For testing your ideas, you will create a new branch using GitHub Desktop (you do not want to mess with the main branch, do you?). In this new branch, you can experiment freely without affecting the stable code in the main branch.

NOTE: When you will be happy with your changes, you will merge them into the main branch, so the main branch always contains stable code.

You can create a new branch in GitHub Desktop by clicking on the menu Branch > New branch... and following the instructions.

IMPORTANT: You have to name the new branch for what you are going to do in this branch.
For example, if you are going to plot the ECG data, you can name the branch plot-ECG, or plot-raw-ECG in a first step, and next create a new branch plot-rescaled-ECG.

5.1. Rescale the ECG data to standard units¶

The ECG recording equipment manufacturer's instructions specify:

Leads recorded  : I, II, III
Sampling frequency : 1000 Hz 
A/D converter gain : 1024 µV per unit

5.1.1. Conversion to mV¶

Using the A/D converter gain information, we can convert the raw ECG data into standard units (millivolts) by applying the following formula:

$\text{ECG}_{\text{mV}} = \text{ECG}_{\text{raw}} \times 1024 \, \mu V$

5.1.2. Conversion to seconds¶

Using the sampling frequency information, we can convert the time axis to seconds:

$timestamp_{\text{s}} ={timestamp_{\text{raw}}}/ {1000}$

6. Improve readability¶

This is the most crucial aspect of writing data analysis code, as it will save you time and effort in the long run. Take good habits from now on.

6.1. Why? To make your code easier to read and understand.¶

Making your code more readable and understandable is essential, especially for you in the future.

  • Are all variables and functions named appropriately?

    • If no, you should rename them to be more descriptive.
      • A variable is named for its purpose/content (e.g., num_ecg_leads).
      • A function is named for its action (e.g., plot_one_ecg_lead), and its action should be a single, clear task.
    • If yes, you should ask a colleague for feedback, and likely incorporate their suggestions.

  • Do you have pieces of code that are the same at different places (e.g., copied from elsewhere)?

    • If yes, you should refactor your code to eliminate duplication. This will make your code more readable and maintainable. The solution is to create a function to replace the duplicated code.

  • Do you have long code blocks (more than 20 lines)?

    • If yes, you should consider breaking them up into smaller, more manageable functions.

  • Do you have a Markdown cell explaining the why you are doing this in the next Python code cell?

    • If no, you should add one to improve the readability and maintainability of your code.

  • Do you have comments explaining your code?

    • If no, are you sure that it is because your code is self-explanatory?
    • If yes, you should rethink them, to ensure that they are concise, and helpful (e.g., use docstrings for functions). Maybe you will no longer need a comment if you rename a variable or function?

6.2. How? Using Git branches.¶

In your attempt to improve code readability, you will make mistakes along the way, and that's okay.
Before starting, use GitHub Desktop to create a new branch in your Git repository. In this branch, you will work on your improvements without affecting the already existing codebase.
Once you are satisfied with your changes, you can merge your improvements back into the main branch (maybe after reviewing them with a colleague... just to be sure).
